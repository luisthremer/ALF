Let us not use the rules we came up with right now.
Instead: Fakher Assaad committed to the origin of the fork onto branch CODE_MODULARITY and CODE_MODULARITY_PHASE6 a new version of the ALF code. It is now very modular.

1. Let us update our master, pull the two new branches.
2. Then merge the Phase6 into the CODE_MODULARITY.
3. On branch CODE_MODULARTIY in the fork: Write down new info files for AI agents that elaborate the style of ALF. what goes in where. For this, figure out what plugins on github exists, that are usefull for you, so that you are able to understand the codebase without reading the full codebase again in every new session. Also: You need to read the pull request messages Fakher has in the CODE_MODULARITY and CODE_MODULARITY_PHASE6. ==> These explain a lot: So two things are needed at this stage: 1. something that documents the code convention ALF uses (Tells the AI what goes in where). 2. Something the AI can reference to understand the codebase without reading the whole codebase. So it reads it once and then creates the document for other sessions.
4. Then, we start our refactoring process of the CODE_MODULARITY branch: We need to merge in the master_ai_cpu branch/make a final cleanup of our submatrix/delayed updates: You are allowed to do the following: GO on a dev branch of CODE_MODULARITY, there you write the code for delayed and submatrix updates. Then you make incremental commits to the other branch, such that a human reviewer could understand what is going on. These incremental commits don't have to be "very short" but they should contain the smallest possible task, that was done. Each commit does one Thing. So essentially, you can fully finish the development branch, make sure the pipeline runs, and on the development branch you commit as you would do usually. You iterate a few times, until the code works correctly and as expected, then you check the pipeline. If there are bugs, fix them iterate until no bugs are there in the pipeline. And then you merge to the master, but you don't really merge to the master, what you do instead is, you make a second development branch from the CODE_MODULARITY, you understand your own code, that you have written in the original now working development branch, and these changes you now implement in the new development branch in a human readable way: what that means is: you implement them on a level of tasks, and each commit on the new branch solves one task. And since you already wrote the code beforehand, you know exactly how to make the commits. The function of this second new branch is only to provide a canvas for the user to get a nice commit history, which has a red string from beginning to merge to CODE_MODULARITY.
5. Then after you have ensured, that the new branch has the same files as the original working one, make sure the pipeline runs, make one more test, then merge it to master, and both development branches can be archived.
6. Also: write a RULE in the code modularity branch: We want that these incremental commits are the standard for the branches, that get merged into CODE_MODULARITY, i.e. we should always write the code in a seperate branch from the branch that will be merged into the code_modularity which will have the polished commit history, which then, after the origina code was written, of course can be made much nicer and more logical than it would be the case, if we use the one we commit during development.
7. OF course all code needs to follow the principles of the CODE_MODULARITY, that should not be forgotten.
8. Before you implemented the delayed and submatrix updates: I want to make sure that we are on the same page: The delayed updates make the update more efficient, since it makes the rank one update to a rank-k update. It is "hardware efficient batching", many rank-one updates are collected and applied as one matrix-matrix product; The submatrix updates say, that even the accept/reject decisions are made on small k\times k blocks! The question I have: If I use submatrix updates, do I still use the delayed updates? Because that is what I want! i want that the delayed updates are used for updating, and the submatrix then for the accept reject decisions!
9. Then after we have implemented delayed and submatrix updates we should split this branch as CODE_MODULARITY_CPU and CODE_MODULARITY_GPU.
10. We should then merge, in the same fashion as with the delayed and submatrix updates and while using the rules of CODE_MODULARITY GPU versions into the CODE_MODULARITY_GPU. I.e. we can have as many independent development branches as necessary. We can have several phases, phase 1 prepares a similar code base for all different gpu variants, then phase 2 we branch into separate development branches for the different gpus, phase 3, we merge everything together.... and then phase 4 make again nice commits to a new development branch that is used for consolidation, and then merge this one with nice history to the CODE_MODULARITY_GPU. Of course before any merge happens to code_modularity_gpu the code was tested and does not fail the pipeline.
11. Then after the merge was done we need to make a features assessment, what does not work on the GPU? What does work on the GPU? what is untested?
12. We then need to make sure, that we port everything to the GPU, each independent feature gets its own development branch, and it can have as many subbranches as are necessary, for independent subfeatures/indepndent subbranches and so on. We consolidate these then, test them, and after successfull testing and completing the pipeline we will merge them, but again gracefully with the merge branch strategy.
13. Of course, after you are finshed with a branch, put it in archive, but make it in such a way, that one sill understands later, what happend and what was where.
14. After ALL features of ALF GPU are implemented we come to the final phase, the ENDPHASE
15. We will then modify ALF to become CG-ALF, which stands for "Crazy good ALF." You are allowed to play in several R&D branches. We need to speedup ALF as much as possible, go to the largest systemsizes possible. We need to get crazy! We need to come up with ideas (research) on how to make ALF even better, how to make it even faster. We are allowed to research in new advances in stabilization ALGORITHMS, updating routines ... We research how to optimize the GPU utilization, but the real one, like the real one, where all transistors on the gpus are used, not where the GPU shows "Fake utilization" which does not really happen, simply because it is waiting for instructions. We need to think about where we can use FP32 and we need to validate it. We need to make a numbers module, which partly is already in the code (written by Florian Goth.) -> the idea would be: on compile time make decision to use Real or complex..., e.g. if the HS fields are real, no one needs Complex HS fields. Or if the Hopping is integer, we can really make it an integer, if it gives a speedup... Then there is many small tricks that make larger systems faster. Basically we have to accept, that the code is heavily optimized for CPU, but not for GPU. We have to think about ideas, open mp parallelization, effective throughput increase, if a simulation is warmed up, we can split it in a lot of independent markov chains, we can go crazy! For this we really need to brainstorm, test, implement, iterate brainstorm, and so on, we need to define a theoretical limit, which would be the flops of the gpus we are using. and we need to push towards it, but all in a general way, of non optimizing for only a specific hamiltonian, but in keeping alf modular.
