# Intel Max 1550 vs H100: regime of each phase, upper bounds, batched multi-walker rewrite

Branch `intel-batched` (from `gpu-port-unified` 33a62652), session 2026-11-13 01:50-03:45 (SuperMUC-NG Phase 2, oneAPI 2025.3.0, 1 node per job,
`-p preempt`). "C" = measured (job id given), "E" = estimate or data-sheet number.
Sources, job scripts and raw outputs: `docs/gpu/scripts/intel_batched/` (`ib_bench.cpp`, `ib_omp.F90`, `ib_wtest.cpp`, `ib_s1.sh`, `ib_s2.sh`,
`ib_tput.sh`, `ib_tput32.sh`, `ib_build.sh`, `ib_sum.py`; raw data in `data/<jobid>/`). Remote: `$SCRATCH/large_prompt/batched/`.
Earlier measurements used and not repeated: Phase 7 per-kernel profile (`docs/gpu/sessions/supermuc_large_prompt/phase2/team/p7/NOTES.md`, "p7"),
Phase 6 batched design study (`.../p6/DESIGN.md`, "p6").

**Summary.** The Max 1550 does not have more FP64 than the H100 for this code: a tile (the unit a process gets) has 39 % of the H100's FP64 matrix rate,
and with all 8 tiles of a node busy its zgemm rate drops by a third (13.5 -> 9.1 TFLOP/s at N = 576, C). The code is not HBM-bandwidth bound at L = 24
(G is L2-resident): one chain per tile is bound by host submission (3 us per async op, ~170k ops per sweep); at 4 chains per tile (CCS 4) the big gemms
run at the tile's peak and the remaining time is under-fill. Tonight's binary gives **0.955 sweeps/s per card at L = 24** (H100 1.176, gap 1.23x) and
**0.179 at L = 32** (H100 0.232, gap 1.29x) (C, jobs 560868/560869). Batching the update block over W walkers (kernels written, bitwise checked) speeds that
block up 1.7-1.9x per tile at L = 24 (C, emulation) = +7 % of the sweep, and nothing at L = 32. The L = 24 H100 throughput needs the whole multi-walker
engine plus a remap of the observables kernels (E: 1.30 sweeps/s per card); L = 32 is at best a tie after the full rewrite (E).

### 1f. Observables `corr` kernel: OpenMP today vs SYCL (`ib_bench corr`, job 560873)

The SpinMz form of `corr` (3 complex sums over I per output d, reads G(J,I,1:2), G(I,J,1:2) and diagonals; square lattice, Norb = 1) written in SYCL:
A = the same mapping as the OpenMP kernel (one work-group of 256 per output, `reduce_over_group`); B = two-pass, column-coalesced (B1 terms into
T(d,I), B2 chunked reduction, B3 sum of chunks). Results of A and B agree to 2.3e-16. us per call:

|--|--|--|--|--|

| OpenMP kernels of today, for comparison (p7, alone, L = 24) | `corr l386` 142, `l418` 187, `l450` 319 (different kinds; SpinMz is the heaviest) | | | |

Reading: a plain SYCL version of the kernel with an explicit work-group reduction is **2-4.5x faster than the ifx-generated OpenMP kernel** at L = 24

## 3. Verdict

1. **Regime.** Not memory bandwidth at L = 24 (G is L2-resident; HBM is reached only at L = 32 when walkers are batched). One chain per tile is
   **latency bound** (host submission ~3 us per async op, 6-7 us per synchronous op, ~170k ops per sweep, plus the serial QR panel inside the kernel). The
   production layout (4 chains per tile, CCS 4) is **occupancy bound**: the big gemms already run at the tile's peak (14.3 TF/s for the 4 processes) and the
   rest of the time goes to small or badly mapped kernels (update block, QR panels, observables `corr`).
2. **Hardware.** "By flops the Max 1550 should obliterate the H100" is false for this FP64 complex code: a tile has 39 % of the H100's FP64 matrix rate,
   measured tile zgemm is 13.5 TF/s alone and **9-11 TF/s with the node busy** (C), so one card gives 18-22 TF/s on these gemms. The H100 targets are still
   **above what tonight's code delivers but below the hardware ceiling at L = 24** (needs 5.4 TF/s effective per tile; ceiling 1.7-1.8 sweeps/s per card).
3. **Reachable?** L = 24 throughput (H100 1.176, Max 1550 tonight **0.955 per card, C**, gap 1.23x): reachable only with the multi-walker engine **plus**
   the observables remap and batched QR (E: 1.30); the batched update block alone gives +7 % (C, emulation). L = 24 single chain (gap 1.15x): reachable by
   cutting submissions in the update block (fuse/graph), no batching needed. **L = 32** (H100 0.232, Max 1550 **0.179 per card, C**, gap 1.29x): batching
   the update block gives nothing (C), the other levers together reach ~0.227 (E): **not reachable with any lever measured tonight; at best a tie after the
   full rewrite**. The owner should plan L = 32 production on the H100.

## 4. Design of the rewrite (batched multi-walker, one process per tile, or per CCS slice)

Follows p6 sections 1-5 (lockstep execution, walker as the last array index, per-walker RNG state / files / MPI ids, tempering as local swaps) with the
following changes that the evidence of this session makes:

1. **Bitwise walker-b-vs-alone is not the acceptance test.** The owner's acceptance test is same-seed agreement with the same-compiler CPU build (Mz=F
   1e-13, Mz=T 1e-10) with a planted defect that fails it. Batched oneMKL gemm differs from single calls by at most ~2e-15 (p6 Gate 2) and was bitwise equal
   in `ib_wtest`; p6's no-go reason "batched gemm is not bitwise" therefore does not block. The own element-wise kernels remain bitwise per walker by
   construction (shown, 1d / section 5).
2. **Layout of processes.** Either 1 process per tile with W = 8 walkers (no CCS), or 4 processes per tile (CCS 4) with W = 2-4 each: both reach the same
   gemm rates (1b); for the block, 4 x W = 4 is best (20.4 us vs 22.4 for 1 x W = 16, variant R). Recommended: **4 processes x W = 4 with CCS 4**, because it keeps today's MPI/rank layout, the host work
   (Metropolis, 20 us per walker-block) is spread over 4 processes, and the QR/CGR serial chains of different processes overlap as today.
   W > 4 per process at L = 32 overflows L2 (1d).
3. **Data layout.** `G_d(N,N,N_FL,W)`, `X_d/Y_d/S/M/slot` with a trailing walker index; kernels get the per-walker stride (`alfsb_*_w`). Lockstep: all
   walkers of a process are at the same (slice, block), so b, nd, nfa/nfb are shared; the pending count k differs per walker (`kw(w)` on the device, `kmax`
   as launch range; flush gemm with `kmax` and zero-padded columns in `gemm_batch` mode, or per-walker k in loop mode).
4. **Host threading.** The W Metropolis decisions of one block step are independent. W <= 4: one host thread, loop over w (20 us per walker-block, p7);
   per-walker RNG state swapped with `RANDOM_SEED(GET/PUT)` around each walker's host step (p6 section 4).
5. **Phases in order of payoff per effort:** (a) update block (done: kernels; next: Fortran lockstep), (b) observables with a walker index + remapped
   `corr` kernels, (c) wraps (hopping gemm via `gemm_batch`, `k_vwrap_all`/`k_site_wrap` with w), (d) device QR panel/apply with a batch of matrices per
   launch (one work-group per matrix: fills W work-groups instead of 1; the Phase 4/5 race proof has to be redone).
6. **Switches (planned).** `ALF_GPU_WALKERS=W` (default 1 = today's path, bit-identical), `ALFSB_GEMM_BATCH=0|1`. W = 1 must remain the current code.
