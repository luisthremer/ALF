## 2. Missed items

Severity is relative to the goal "full implementation + full benchmark on SuperMUC-NG Phase 1 and Helma (CPU)".

### 2.1 Blocking
- **B1. SuperMUC-NG Phase 1 shuts down at the end of 2026.** LRZ aims to run it until 31.12.2026 at reduced capacity;
  unused CPU hours expire then and cannot move to Phase 2, which is GPU-only and does not accept CPU-only codes. A status
  snapshot from 2026-08 showed many nodes down or drained. ⇒ The SuperMUC benchmark has about 8 weeks, including queue
  time. [collab.dvb.bayern/lrzpublic/end-of-operation-of-supermuc-ng-phase-1-3148941213.html;
  doku.lrz.de/gcs-regular-project-on-supermuc-ng-10746583.html; status.lrz.de/affected/hoechstleistungsrechner]
- **B2. O(N⁴) setup when `Symm=.T.`** ✔ `Op_V_is_symmetric` (`Operator_mod.F90:1025-1101`, called from
  `Hamiltonian_main_mod.F90:1061`) forms two dense N×N products of (I + g V) with gfortran `matmul` for every vertex
  and flavour: 2·N_FL·n_op dense N×N matrix products, i.e. ∝ N⁴ for Hubbard. Measured: 24 s at N = 400 (M1). Extrapolated:
  ~2 days at N = 3600 and ~1.5 months at N = 8000 (with MKL/ifx faster, still prohibitive). This is **baseline ALF code**
  (present in `ALF_baseline`). The override flag is a private variable, not a namelist key (only Kondo sets it). The Start
  template uses `Symm=.T.`. ⇒ Large-N benchmarks need either `Symm=.F.` (different Trotter scheme) or a change in baseline
  code (e.g. trivially true if all `Op_V` are diagonal; or a sparse commutator check on the supports). This touches
  default behaviour outside the scheme and needs a user decision.
- **B3. The branch has never been built with an Intel toolchain.** The `SUPERMUC-NG` preset uses `mpiifort` with
  `-fp-model fast=2 -ipo -parallel -qopenmp -heap-arrays 1024`; the `HELMA` preset uses ifx with `-static -xHost`. Unknown:
  whether the code, the trace build and ctest 36 (which links whatever `Prog/*.o` exist, and runs without `mpiexec` under
  MPI) work there. The regression/trajectory harnesses assume the Mac paths.
- **B4. The cluster software stacks have changed under the presets.** SuperMUC (since 24.03.2026): default
  `stack/24.6.0`, oneAPI 2025.3 (ifx/icx default; `ifort`/`mpiifort` only after `module load intel-legacy-compilers`);
  `hdf5/1.10.7-intel21` from the preset is not confirmed in the new stack; the old `stack/22.2.1` is reachable but
  unsupported. [doku.lrz.de/os-upgrade-to-sles-15-7-2547191989.html] Helma's preset versions (intel 2025.3.1,
  intelmpi 2021.17.0, mkl 2024.2.2) are unverified against the docs.

### 2.2 Important
- **I1. Helma CPU = AMD.** The `cpu` partition has 312 nodes with 2× AMD EPYC 9965 (Zen5c, 384 cores, 768 GB,
  SMT off, likely 8 NUMA domains of 48 cores); 1–64 nodes, 24 h; `preempt_cpu` 1 node, 48 h. Access requires a separate
  Helma-CPU application. Consequences: MKL on AMD may not pick its best code path (`MKL_DEBUG_CPU_TYPE` is gone since
  MKL 2020.1); compare with AOCL-BLIS/OpenBLAS; `-xHost` with ifx on AMD must be tested. GPU nodes require a GPU request,
  so they are not suitable for CPU benchmarks. [doc.nhr.fau.de/clusters/helma/; hpc.fau.de/access-to-helma-cpu/]
- **I2. Stabilisation is the real limit at large N.** After acceleration, the G update and the stabilisation are both
  O(βN³) BLAS-3; their ratio does not shrink with N, so our ~60 % stabilisation share will persist. Sun/Xu's public
  benchmark data (submatrix-T, honeycomb) show stabilisation at 23–26 % of the sweep. ALF's update share f_U at
  N ≥ 3600 and its dense vs checkerboard hopping cost are unmeasured. Levers: larger `Nwrap` (precision), checkerboard,
  threaded QR. Expected total speedup at N = 3600 on a 48-core Intel node: **≈2–4×** (Amdahl estimate, assumptions in §3).
- **I3. Threading.** ALF has no OpenMP regions (`!$omp` absent in `Prog/` and `Libraries/`), so threads come only from
  threaded MKL. Sun & Xu's gains rely on threaded BLAS: at n_d = 256 with 8 threads, update time 47.5 → 14.5 s
  (submatrix) and 71 → 39 s (delay) (SciPost 18, 055, Fig. 3b). The ratio part does not thread at all; the submatrix
  scheme shrinks exactly that part, so it benefits more. Our benchmarks are single-thread only.
- **I4. Lazy validation.** A typo in `Sequential_scheme` aborts at the first `WRAPGRUP`, i.e. after the (B2) setup:
  hours into a large-N job.
- **I5. `Prog/default_parameters_generic.py` is ALF's own file** (not pyALF's, as the report says) and lacks the new
  keys, so parameter files generated from it cannot set the scheme.
- **I6. No provenance in `data.h5`.** Scheme and N_delay live only in `info` (baseline stores no `VAR_QMC` there).
  HDF5-based analysis cannot tell which scheme produced the data.

### 2.3 Minor
- `Op_set` sets the rank of a diagonal N>1 operator to N even if some eigenvalues are zero (`Operator_mod.F90:358`):
  relevant for sizing a rank-N extension.
- Licence: the modified files (`Wrapgr_mod`, `upgrade_mod`, `QMC_runtime_var_mod`, `Makefile`) carry no §7 modification
  notice; `Trace_updates_mod.F90` is headed "2016-2022 The ALF Project".
- New parameters are not in `Documentation/files.tex` nor in the `Start_Tempering` parameter files.
- Baseline latent bug in Z2_Matter: stale `I1` and `Op_set(Op_V(nc,1))` inside the nf loop
  (`Hamiltonian_Z2_Matter_smod.F90:358-366`).
- NaN checks exist only in debug builds; `-fp-model fast=2` / `-ffast-math` may remove them.
- Checked without findings: stack arrays, `MPI_BCAST` of the CHARACTER(64), integer kinds, STAB/LOG variants, projector and
  `g_t` in the hook, type-3/4 fields and `Amplitude` (random numbers drawn before either path), `Propose_S0`, phase and
  N_SUN, `weight_reconstruction`, tempering `info` path, confout (always flushed), RNG (one draw per proposal).

### 2.4 Memory at large N (k = 256, N_FL_eff = 2)
Delayed X+Y: 59 MB (N = 3600), 131 MB (N = 8000). Submatrix Cw+Rw+Mw: 44 / 98 MB, Γ̃⁻¹ ≈ 2 MB. Negligible next to GR
(0.41 / 2.05 GB for two flavours) and the UDV stacks. Per-rank memory at N = 8000 is tens of GB, which limits ranks per
node on SuperMUC thin nodes (90 GB usable).

negligible at large N (≥ 14 blocks per slice).
